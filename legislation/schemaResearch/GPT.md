Architectural Blueprint for WSL Data Integration

This blueprint structures Washington State legislative data around Bill and Version entities with linked satellites.  The Bill table (one record per bill number per biennium) holds invariant data: bill number/prefix, biennium, original titles, prime sponsor, final outcome (passed, veto, etc.), session-law chapter, and affected RCW sections.  The Version table (one record per substantive version such as substitutes or engrossments) includes version code, publication dates, active flag, version‐specific sponsor(s) (including committee sponsors), document URLs, amendments, reports, and fiscal notes.  Satellite tables capture related data with explicit foreign keys: e.g. CommitteeMeeting (with AgendaID, date, location) and CommitteeMeetingItem link hearings to bills ￼ ￼; RollCall and Vote tables record floor votes for each bill (motion, date, counts, and individual votes) ￼; CompanionBill relates House/Senate counterpart bills (via BillID and Biennium); BillAmendment (or Amendment) links amendments incorporated into each version; and Testimony or similar (if exposed) would link hearing testimony to meetings.  Each satellite’s foreign key parent is explicit: e.g. CommitteeMeetingItem → CommitteeMeeting (by AgendaId) and to Bill (by BillId), RollCall → Bill, Vote → RollCall, CompanionBill → Bill (and vice versa).

Bill (PK: BillNumber, Biennium) – e.g. BillNumber (int) and biennium “2025-26”; Prefix (HB/SB) and DisplayNumber from LegislationService; ShortDescription, LongDescription, LegalTitle (original short/long titles) ￼; PrimeSponsorName and PrimeSponsorID (original legislator) ￼; final status flags (PassedBoth, PartialVeto, Veto – derived from SessionLawService or LegislationService status) ￼; SessionLawChapter (int) from SessionLawService ￼; aggregate AffectedRCWSections (derived via RcwCiteAffectedService lookups, likely a separate Bill–RCW linking table).

Version (PK: BillNumber, Biennium, VersionCode) – version string like “S1” or “H4.E”; Agency (originating chamber), Active flag (True if floor-passable) ￼; version‐specific fields: IntroducedDate (datetime) ￼; sponsorship (VersionSponsorName, VersionSponsorID) ￼ – note: if a committee takes over (e.g. on a substitute), the committee’s name appears here while Bill.PrimeSponsor remains the original human sponsor; ShortTitle/LongTitle may be inherited or differ per version (from LegislationService); booleans for requested fiscal notes or budget impacts (StateFiscalNote, LocalFiscalNote, Appropriations, etc.) ￼; indicator AmendmentsExist (true if this version incorporates amendments) ￼; CompanionBills (list of companion BillIDs and status) ￼.  The Version table also links to documents: primary text URLs (PDF/HTML/XML) for that version.  These come from LegislativeDocumentService – for each documentClass (e.g. bill text, amendments, reports) you retrieve records with fields like HtmUrl/PdfUrl and BillId ￼ ￼, which populate a Document table keyed by (BillNumber, Biennium, VersionCode, DocType).  Fiscal notes (from FiscalNoteService) likewise link to Version (not shown in example services, but if available, store note text and dates per version).

CommitteeMeeting (PK: AgendaId) – fields: Agency, date/time, Building, Room, address, Cancelled flag, RevisedDate, ContactInfo, CommitteeType, Notes ￼.  CommitteeMeetingItem (PK: AgendaId, Order) – each meeting’s agenda items: BillId (FK to Bill), HearingType, Description, ItemOrder ￼.

RollCall (PK: BillNumber, Biennium, SequenceNumber) – for each vote: Agency, Motion (e.g. “Final Passage”), VoteDate, counts of Yea/Nay/Absent/Excused and member lists, plus list of individual Vote records (each with MemberId, Name, VoteChoice (Yea/Nay/etc)) ￼.

CompanionBill (composite PK: BillNumber, Biennium, CompanionBillNumber, CompanionBiennium) – each companion pair with status.

BillAmendment – links an amendment (which may be treated as a special Version or as a separate “Amendment” entity) to the bill.

(Cardinalities: One Bill has many Versions, RollCalls, Companions, Amendments, Meetings; one Version belongs to one Bill; one RollCall has many Votes; one CommitteeMeeting has many CommitteeMeetingItems, etc.)

Field Dictionary

Below we map key service fields to schema columns (with any notes):
	•	Bill.BillNumber (PK) – LegislationService BillNumber ￼ (integer).  Biennium – LegislationService Biennium.  Prefix (HB/SB) and DisplayNumber – from LegislationService (e.g. ShortLegislationType / DisplayNumber fields returned by summary calls ￼).
	•	Bill.ShortDescription, LongDescription, LegalTitle – from LegislationService.GetLegislation: <ShortDescription>, <LongDescription>, <LegalTitle> ￼ (original titles).
	•	Bill.PrimeSponsorName, PrimeSponsorID – from LegislationService.GetLegislation: <Sponsor> (name) and <PrimeSponsorID> (person ID) ￼.  (If a substitute version has a committee sponsor, that name will appear in Version.Sponsor instead.)
	•	Bill.FinalDisposition – derived from Legislative status or session law: e.g. if SessionLawService returns <Veto> or <PartialVeto> true ￼, mark accordingly; else if legislature passed both chambers (LegislationService passed queries) set “Passed”; otherwise “Failed/Died.”
	•	**Bill.SessionLawChapter – SessionLawService.GetSessionLawByBill: <ChapterNumber> ￼ (int).
	•	Bill.AffectedRCWSections – aggregate from RcwCiteAffectedService (no direct bill→RCW call; a reverse lookup by querying known RCW cites yields which bills affected them). Store in a separate BillRCW table.
	•	Version.VersionCode – implicit (e.g. “S1” for first substitute, “E” if engrossed).  LegislationService gives SubstituteVersion and EngrossedVersion numbers in summary endpoints ￼.
	•	Version.Active – LegislationService summary <Active> flag ￼ (true if this version may be passed on floor).
	•	Version.IntroducedDate – LegislationService.GetLegislation: <IntroducedDate> ￼.
	•	Version.SponsorName, SponsorID – LegislationService.GetLegislation (per version): <Sponsor> and <PrimeSponsorID> ￼.  (E.g. on a substitute, SponsorName may be a committee, but Bill.PrimeSponsorName remains original.)
	•	Version.StateFiscalNote, LocalFiscalNote, Appropriations, RequestedByGovernor, … – LegislationService.GetLegislation: boolean fields like <StateFiscalNote>, <LocalFiscalNote>, <Appropriations>, etc. ￼.  These indicate existence of fiscal notes or budget issues; actual note content (if needed) requires FiscalNoteService (not shown).
	•	Version.AmendmentsExist – LegislationService.GetLegislativeStatusChanges (or CurrentStatus) <AmendmentsExist> ￼ (true if amendments were acted on).
	•	Version.Companions – LegislationService.GetLegislation: under <Companions>, lists <Companion><BillId><Status> pairs ￼.  Map to CompanionBill table (BillID + Status).
	•	Document (satellite)* – LegislativeDocumentService.GetDocumentsByClass or GetAllDocumentsByClass returns records with <Name>, <Type>, <Class>, and URLs.  Key fields: <HtmUrl> and <PdfUrl> (strings) ￼ linked to BillId.  We store in a Document table: (BillNumber, Biennium, DocName, DocType/Class, HtmUrl, PdfUrl, dates).  (For example, bill text has Class=“Bill”, amendments “Amendment”, reports “BillReport”, etc.) ￼ ￼.
	•	CommitteeMeeting.AgendaId – CommitteeMeetingService.GetCommitteeMeetings: <AgendaId> (int) ￼.  Other fields: <Agency>, <Date>, <Building>, <Room>, <Address>, <Cancelled>, etc ￼.
	•	CommitteeMeetingItem* – CommitteeMeetingService.GetCommitteeMeetingItems: for each item, <AgendaId> (FK), <BillId> (string, link to Bill), <HearingType>, <ItemDescription>, <Order> ￼.  (Map to columns MeetingItem.HearingType, Description, ItemOrder with FK AgendaId.)
	•	RollCall.SequenceNumber, VoteDate, Motion – LegislationService.GetRollCalls: <SequenceNumber> (int), <VoteDate> (datetime), <Motion> ￼.
	•	RollCall.Agency – which chamber (“House”/“Senate”) ￼.  Vote counts: <YeaVotes><Count>, <NayVotes><Count>, etc ￼.  Member lists (<MembersVoting> strings) can be stored or ignored.
	•	Vote* – in GetRollCalls output, <Votes><Vote> entries each have <MemberId>, <Name>, <Vote> (Yea/Nay/Absent/Excused) ￼.  We map these to a Vote table (FK to RollCall by BillNumber/Biennium/Sequence).
	•	CompanionBill* – LegislationService.GetLegislation: each <Companion> in <Companions> includes Biennium, BillId, Status ￼.  Store as pairs (BillId↔CompanionBillId) with status.

(Fields not explicitly provided via these services – e.g. “striker” links, gut-and-replace – are not clearly exposed. Any undocumented relationships should be inferred or validated from textual clues or human review.)

Sync Decision Logic

Overview: To sync a bill’s data, we generally start with broad “much-from-little” calls and supplement with targeted calls:
	1.	Get base Bill/Version data: Call LegislationService.GetLegislation(biennium, billNumber).  This returns one or more <Legislation> entries (original and substitutes) including status info, sponsor, titles, etc ￼ ￼.  From this we populate the Bill record (once) and Version records (one per <Legislation> entry).  It yields most invariant data (titles, sponsor, introduced date, and for each version whether amendments exist or fiscal notes are flagged) in one call.
	2.	If we need history/status: The above call gives the current status line.  For full status timeline, use GetLegislativeStatusChangesByBillNumber (or by date range) ￼.  That returns all status changes (each with <HistoryLine>, <ActionDate>, flags like <Veto> etc).  Append these to a BillHistory table if needed.  Note: LegislationService status strings are textual and may be inconsistent; if PartialVeto or Veto is true on any status, cross-check with SessionLaw data.
	3.	Fetch session law/chapter: If the bill has been enacted, call SessionLawService.GetSessionLawByBill(biennium, billNumber).  This yields <ChapterNumber>, EffectiveDate, and <Veto>/<PartialVeto> flags ￼.  Use this to set Bill.SessionLawChapter (and record the chapter assignment date).  Without this call, we cannot get the chapter number.  (Detecting “passed but not yet chaptered” state: if LegislationService shows bill passed both chambers but SessionLaw returns nothing, treat as pending chapter.)
	4.	Document URLs and text: For each version, retrieve document URLs via LegislativeDocumentService.  Two main approaches: (a) GetAllDocumentsByClass(biennium, class) for classes like “Bill” (bill text) or “Amendment” or “BillReport”; filter results by BillNumber; or (b) GetDocumentsByClass(biennium, class, namedLike=billNumber) to narrow.  The returned <LegislativeDocument> entries provide HtmUrl and PdfUrl for each document ￼.  Store these in a Document table keyed to the Version (or Bill).  This fetches most of the textual artifacts in a few calls.
	5.	Sponsors: The original human sponsor came from step 1.  If a version’s sponsor is a committee (as indicated by name), record it at Version level and retain the Bill-level prime sponsor as originally set.  No additional call is needed; GetLegislation already provided <Sponsor> and <PrimeSponsorID> ￼.
	6.	Amendments: If AmendmentsExist=true on a version, we may call GetAmendmentsForBiennium or GetAmendmentsForYear (LegislationService) to list amendment bill numbers/names for that bill (not shown here, but available).  Those amendment bills can be handled like separate bills/versions or noted in a BillAmendment table.
	7.	Fiscal notes: The Booleans from step 1 show whether a fiscal note exists.  To retrieve content, call the FiscalNoteService (not documented above).  If service is limited, one may need to scrape OFM or a separate API.  In general, to get full fiscal notes, assume using a specialized path rather than LegislationService.
	8.	Committee actions: Hearing schedules/actions for bills are available via CommitteeMeetingService.  You might either: (a) filter meetings by date range (GetCommitteeMeetings(begin, end)) and then filter items by BillId, or (b) if a GetHearings endpoint exists in LegislationService (it does: operation 4 “Returns list of committee hearings for the bill”), call that with (biennium, billNumber).  The latter may give a quick list of hearings (if implemented).  Otherwise, periodically call GetCommitteeMeetings or GetRevisedCommitteeMeetings for the session dates.  For each meeting with matching bill, use GetCommitteeMeetingItems(agendaId) to get the specific bill’s agenda item ￼.  This populates the CommitteeMeeting and CommitteeMeetingItem tables.
	9.	Roll call votes: Call GetRollCalls(biennium, billNumber) ￼.  This returns all floor votes on that bill (one or more <RollCall> entries).  Store each RollCall with counts and store each <Vote> child row as an individual record (mapping MemberId, Name, VoteChoice).  If LegislationService returned multiple versions, you may repeat for each, but in practice roll calls apply to a specific bill number (amendment votes come under amendment bill numbers).

Input costs vs output:
	•	Much-from-little: GetLegislation by bill number is a workhorse (one call yields all version info) ￼.  Similarly, GetAllDocumentsByClass by class/ biennium yields many URLs at once ￼.  GetCommitteeMeetings by date gives many meetings.
	•	Little-from-much: Using LegislationService “since date” or “by status” queries is more granular. For example, GetLegislationIntroSince(date) returns only new bills, less efficient for historical backfill.  FiscalNoteService (if it exists) likely requires specifying bill/version and may return large text blocks, so use only when needed.

Disambiguation cases:
	•	If GetLegislation shows a summary status (e.g. “Passed Legislature”) but we see no chapter, use GetSessionLawByBill to confirm and get chapter ￼.  Conversely, a chapter found implies final passage.
	•	LegislationService does not include full fiscal note text – only flags.  Thus, for completeness we must query FiscalNoteService separately (and in sync logic, fetch only bills with notes flagged).
	•	To list all versions of a bill, GetLegislation gives each version as a separate <Legislation> entry ￼, including original and substitutes.  For each version, documents can be fetched by filtering on bill number and class (DocumentService) as above.

Edge Cases & Temporal Notes
	•	Sponsor inheritance (committee sponsors):  When a committee sponsor replaces a human sponsor (often on a substitute version), LegislationService returns the committee name in <Sponsor>.  We record that on the Version, but do not overwrite the Bill’s original prime sponsor.  (Our schema separates Bill.PrimeSponsor from Version.Sponsor.)  The original sponsor is stored at Bill-level (from the first <Legislation> entry), even if later versions list only a committee ￼.
	•	Pre-chapter lag (“passed but not yet chaptered”):  A bill can pass both chambers and await chapter assignment.  During that window, GetSessionLawByBill returns nothing (no chapter).  We detect this by: (a) LegislationService indicating final passage (e.g. via PassedLegislature queries) or Senate/House pass statuses, and (b) no chapter found yet.  We should mark the Bill as “Enacted but Pending Chapter.”  Typically, chapters are assigned a few days after adjournment; to capture the chapter later, poll SessionLawService periodically.  There are no provisional chapters in SOAP; one must rely on the actual update.
	•	Silent updates: Some data can change without a new bill version.  For example, document URLs or timestamps may be corrected after initial posting.  Likewise, a fiscal note might be revised.  To detect such updates, use the timestamps provided by services: LegislativeDocumentService returns LastModifiedDate for URLs ￼, and CommitteeMeeting has RevisedDate ￼.  By comparing these, a sync job can re-fetch the document or meeting details.  We recommend polling: during session, run daily (or more) to catch hearing and vote changes; off-session, weekly or monthly for status and document updates.
	•	Redundancies & Gaps:  Some endpoints overlap or are under-documented.  For instance, LegislationService.GetHearings (op 4) is redundant with CommitteeMeetingService.  Always prefer CommitteeMeetingService for full committee data.  Also, the LegislationService says “RCW Cites Affected” via session law but it only lists which bills affect a given RCW (RcwCiteAffectedService) ￼, so our “AffectedRCWSections” for a bill must be built by reverse lookup (not direct).  If any expected field lacks data, note the uncertainty: e.g., a “gut and replace” relation is not explicitly given by services.
	•	Temporal stability:  Most Bill-level fields (titles, original sponsor, bill number) are stable once set.  Version‐specific fields (dates, active flag) also only change if a new version supersedes it.  By contrast, status histories and document URLs can update.  Use the services’ timestamps or revision queries to detect changes.  There are no built-in change tokens, so our sync must rely on polling and comparing data.
